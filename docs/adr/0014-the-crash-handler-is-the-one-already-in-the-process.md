# ADR 0014 — The crash handler is the one already in the process

- **Status:** accepted
- **Date:** 2026-12-07

## Context

The roadmap asks for Crashpad: an out-of-process handler, minidumps uploaded to an endpoint,
symbols published from CI, and a script that symbolises a dump.

Sonora already has Crashpad. It is inside `libcef.dll`, it has been in every build since
week 2, and it is the same Crashpad — CEF ships Chromium's crash reporting, with the handler
running as a separate process, the annotations, the rate limiting and the upload. Adding a
second one would mean vendoring a large dependency, building it, and then having two crash
handlers install two exception filters in one process and argue about which of them owns the
fault.

That would be the second time this project was asked to add machinery it already had.
[ADR 0009](0009-the-update-server-is-a-signed-file.md) was the first, and the shape of the
answer is the same: the interesting work is not the handler, it is what the handler does with
what it collects.

There is also a constraint that is easy to miss and expensive to discover: **a minidump
without the matching PDB is a list of hexadecimal addresses forever.** Windows minidumps carry
module names, build ids and addresses; the symbols live in the PDB that the linker produced
for that exact build, and nothing reconstructs them later. So the part of this week that
cannot be deferred is not the collection — it is publishing the PDBs with the release, keyed
so that a dump from any build can find its own.

## Decision

**Crash reporting is CEF's, configured by a file next to the executable, and every release
publishes its PDBs.**

### The configuration is a file, not code

CEF reads `crash_reporter.cfg` from the directory of the executable at startup — before
`CefInitialize`, before anything in `src/shell` runs. So this is a file in the payload
(`installer/crash_reporter.cfg.in`, generated by CMake and installed beside `Sonora.exe`)
and not a call anybody makes.
It sets the server URL, the rate limit, the maximum number of dumps kept, and the crash keys
that may be attached.

Two consequences of it being a file rather than code are worth having on purpose. It can be
edited on a machine that is crashing, by somebody diagnosing it, without a rebuild. And it can
be deleted, which turns crash reporting off completely — which is the honest off switch for
somebody who does not want dumps leaving their computer, and it is documented as one.

### There is no crash server, and the endpoint is local

[ADR 0009](0009-the-update-server-is-a-signed-file.md) decided this project does not stand up
services it cannot promise to keep running, and a crash endpoint is exactly such a service:
every installation would post to it, forever, including the ones from three years ago.

So the configured URL is a local one, `http://127.0.0.1:9911/crashes`, and
`tools/crash_receiver.py` receives the multipart POST and writes the `.dmp` beside the
annotations. It was going to be fifty lines; receiving what Crashpad actually sends -- a
gzipped body with no `Content-Length`, framed as `Transfer-Encoding: chunked` -- took rather
more, and the two halves of that are in the consequences below. That is enough to exercise the whole path — crash, handler, upload,
file on disk, symbolised stack — and it is honest about what it is: a diagnostic tool for the
person developing Sonora, not a product feature. A release that wanted to collect crashes
from users would change one line in a configuration file, and would then owe its users a
privacy notice that this project is not in a position to write.

### The PDBs are release artefacts, and this is the part that cannot wait

Every release uploads `Sonora.pdb`, `sonora_helper.pdb` and `sonora-updater.pdb` alongside the
MSI and the update package. They are useless to a user and they are the only thing that makes
a dump from that build readable, ever — and unlike everything else in the release they cannot
be regenerated later, because a PDB is produced by the link and a link is not reproducible
down to the addresses across compiler updates.

`tools/symbolise.ps1` takes a dump and a directory of PDBs and drives `cdb` from the Windows
SDK. It does not vendor a symbolisation stack: `cdb` is on any machine with the Debugging
Tools installed, the script says what to install when it is not, and the alternative — building
Breakpad's `dump_syms` and `minidump_stackwalk` to avoid depending on a tool Microsoft ships
for free — is a week of somebody's time for a script that would still only run on Windows.

### Crash keys are set where the answer is known

`CefSetCrashKeyValue` attaches a string to every dump this process produces afterwards. The
ones set are the ones that a stack trace does not tell you and that decide what to look at
first: the version, whether the build is a release or a development one, the update stage from
the journal, the library's schema version, and whether the audio device started. Five strings,
each of them a thing that has caused a bug in the last eleven weeks.

Not the user's library path, not a file name, not anything that identifies the machine. A crash
report is the most sensitive thing a desktop application sends, and the list of keys is short
enough that a person can read it and decide.

## Consequences

- **The CEF sandbox is still off** ([ADR 0003](0003-serving-the-ui-over-a-custom-scheme.md)),
  and it is the same debt it was in week 10. It has no bearing on the handler working, which is
  why this ADR does not pretend it was addressed here.
- **A crash before `libcef.dll` loads is not reported.** The handler is inside it, so a fault
  in the first few instructions of `Sonora.exe` — the update journal being read, for instance —
  produces nothing at all. That is a real hole and the honest mitigation is that the code that
  runs before CEF is the code with the fewest moving parts: read a file, compare five values,
  start a process or do not.
- **Nothing is proved about the *upload* until somebody runs the receiver**, and it is a manual
  step: the receiver is a script, not a service, so a CI job cannot check that a dump arrives
  without standing one up. Worth knowing before writing one: Crashpad **gzips** the body and
  says so in `Content-Encoding`, unless the handler was started with `--no-upload-gzip`, which
  Chromium does not pass. A receiver that ignores that header refuses every real dump -- and
  if it refuses them quietly, it is indistinguishable from a receiver nobody is uploading to,
  which are the two states this whole ADR exists to separate. What CI does check is that the configuration file ships and that the
  PDBs are attached to the release — the two things whose absence would only be discovered on
  the day a dump needed reading.
- **A deliberate crash is a debug-build flag, and it crashes the browser process only.**
  `--simulate-crash=browser` exists where DevTools does, because an executable that will fault
  on request is a convenience in a debug build and a liability in a release. The renderer half
  of that flag was written before it was tried and it never worked: the plan was to load
  `chrome://crash`, and under CEF that URL does nothing -- the window stays blank, because CEF
  serves a short list of `chrome://` URLs and that is not one of them. The renderer is crashed
  with the DevTools protocol's `Page.crash`, which needs no code here; the flag now refuses
  `renderer` and prints that instead.
- **The version in the configuration file is generated, not typed.** It is a `.in`, and
  `@PROJECT_VERSION@` comes from the git tag like every other version in this project. The
  crash key `sonora_version` is the one that has to match a PDB, but a configuration file
  announcing a version that was never released is a thing a reader has to stop and check,
  and there is no reason for it to exist.
- **Two keys in that file are load-bearing in a way their names hide.** `AppName` decides
  where the crash database goes on Windows, and its default is a folder called `CEF` in the
  user's profile -- so leaving it out does not mean "somewhere sensible", it means Sonora's
  crash reports live under a name that nothing uninstalling Sonora will find. And an
  unrecognised key in an INI file is not an error, it is a line that does nothing: the first
  version of this file set `MaxUploads` and `UploadToServer`, neither of which CEF reads. The
  keys CEF reads are listed in `include/cef_crash_util.h` and nowhere else, which is worth
  knowing before writing a configuration file for it.
- **Dumps accumulate in the user data directory** if nothing collects them: `max_uploads` and
  `max_database_size_in_mb` in the configuration file bound that, and the numbers are in the
  file where somebody can read them rather than in a constant somebody has to find.
